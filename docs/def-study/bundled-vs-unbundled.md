# Bundled vs. unbundled definitions

*Captured from ICERM discussions; first entry in the
[def-study](README.md) collection.*

*Cross-reference: Gusakov–Nelson–Watt (arXiv:2509.10828, 2025),
**"Structuring Definitions in Mathematical Libraries"** — paper-level
treatment of exactly these trade-offs, with four Mathlib case
studies (CFC, graded rings, matroids, graphs). Structured reading:
[`gusakov-nelson-watt-2025.md`](gusakov-nelson-watt-2025.md). The
paper independently arrives at the same operational methodology
described below.*

## The principle

The **conceptually nicest** Lean/Mathlib definition is to bundle an
object together with all of its mathematical properties — types
tell the truth, the right structural unfolding happens automatically,
and a fact about the object follows by `.foo` projection rather than
by carrying a side hypothesis.

But bundled definitions are often **hard to use**. They drag
domain/codomain information through every operation. Composing,
restricting, or extending bundled objects forces type-level
bookkeeping that has no mathematical content. Sometimes the
sledgehammer-shaped object is exactly what you want; very often it's
not.

The standard fix is to **unbundle** — drop part of the typing
precision, accept that the resulting function is no longer
type-distinguishable from junk inputs, and use a convention to
extend the definition to those inputs (Mathlib's choice for many
"junk" cases: return `0` or `default`).

**The best choice cannot be decided without looking at common use
cases.** Whichever convention makes the *applications* clean wins
over the convention that makes the *theorem statement* prettiest.

## Canonical example: the continuous functional calculus

For a normal element `a` of a unital C*-algebra `A` (i.e., `a a* = a* a`),
the Gelfand-Naimark theorem says the C*-algebra generated by `a` and
`a*` is *-isomorphic to `C(spec a)`. The bundled view is a clean
type:

```
cfcStar : C(spec a, ℂ) →⋆ₐ[ℂ] A
```

The morphism sends `id` to `a`, conjugation to `a*`, and is a
*-isometric isomorphism onto the subalgebra. Theorems of the form
"`f(a)` has property P iff `f` has property P on `spec a`" are
immediate from the typed correspondence.

**But.** The most important *use* of CFC is to define new elements
by *composition*: given `f : ℝ → ℝ`, build the operator `f(a)`,
plug it into another expression, restrict, extend. In the bundled
formulation, every step needs:

* Knowing `spec a` (computing or carrying it as data).
* Restricting `f` to `spec a` (a separate continuous-map operation,
  with its own domain).
* Pushing operations through the isomorphism.

So Mathlib instead exposes (in
`Mathlib.Analysis.CStarAlgebra.ContinuousFunctionalCalculus.Unital`)
the **unbundled** version:

```
cfc : A → (ℝ → ℝ) → A
```

That is: `cfc a f` is an element of `A`, parametrized by a bare
function `f : ℝ → ℝ`. Semantically `cfc a f = f(a)` evaluated via
the bundled isomorphism *restricted to `spec a`*; `f`'s values
outside `spec a` are simply ignored (or, equivalently, sent to `0`
in the algebra). The function-typed input is convenient for
composition and lets users write `cfc a (fun x => x^2 + 1)`
without ever thinking about `spec a`.

(Both versions exist in Mathlib. The bundled `cfcL` is available
when you actually need the typed correspondence; `cfc` is the
day-to-day API.)

The cost of unbundling: lemmas about `cfc a f` have to carry a
"`f` is continuous on `spec a`" hypothesis manually, or else they
hold vacuously / about junk. The benefit: every composition is a
plain function composition, no spec-tracking required.

## Project-internal example: `MarkovSemigroup` carrier

We hit the same trade-off in 2026-05-13 for the abstract
`MarkovSemigroup` structure in
`MarkovSemigroups/Abstract/Hypercontractivity.lean`.

**First design (rejected):** the most "bundled" pointwise typing,
`P : ℝ → (X → ℝ) → (X → ℝ)`. The semigroup acts directly on
functions, the statements look like the math: `P_{s+t} f = P_s (P_t f)`.

**The flaw** (caught by `gemini-3.1-pro-preview` vetting): on a
measure space, the actual Bochner integral `∫ h dμ` evaluates to
the *junk value* `0` for non-integrable `h`. For signed
non-absolutely-integrable `f`, the unconditional semigroup field
`P_semigroup` can fail because one side hits `0` while the other
conditionally converges to a non-zero value. The structure was
unsound for its intended downstream use.

**Refactor:** move the carrier to bounded operators on the L²
Hilbert space:

```
P : ℝ → (Lp ℝ 2 μ →L[ℝ] Lp ℝ 2 μ)
```

This is a step *down* from the conceptually-nicest pointwise typing
toward the operator-theoretic typing. On `L²` equivalence classes,
junk values don't exist; the semigroup laws hold flawlessly. The
cost: `IsCore`-style hypotheses now have to bridge between
`X → ℝ`-typed core functions and their `Lp ℝ 2 μ`-typed equivalence
classes (we added an `IsCore_memLp` field for this).

Same pattern as the CFC story: a typing that *describes the math
truthfully* (pointwise functions) was rejected in favor of one that
*makes the operations safe and unambiguous* (Lp equivalence classes).
The "junk value 0" sin was hiding inside the pointwise carrier and
only became visible when we tried to compose semigroup laws under
non-integrability.

## Project-internal example: `IsCore` closure

A subtler instance of the same trade-off, still open as a design
question in `markov-semigroups`:

The Stroock-Varopoulos axiom on `DirichletMarkovSemigroup` takes a
core function `f` and produces a bound on `E(f^{p/2}, f^{p/2})`. But
`IsCore f` doesn't structurally imply `IsCore (f^{p/2})` — closure
under smooth composition is not part of the abstract structure.

**Bundled option:** add `IsCore_smooth_compose : ∀ Φ, IsCore f →
IsCore (Φ ∘ f)` (with hypotheses on `Φ`) as a structural field. Then
`f^{p/2} ∈ IsCore` follows from `f ∈ IsCore` for free.

**Unbundled option (what we chose):** leave `IsCore` minimal; each
call site of `stroock_varopoulos` has to pass `f^{p/2} ∈ IsCore`
and `f^{p−1} ∈ IsCore` as extra hypotheses.

For the eventual concrete instance (Gaussian1D), `IsCore` *is*
closed under smooth composition with appropriate `Φ`, so the
hypothesis is dischargeable. For abstract use, the closure may not
hold (jump processes, finite spaces, etc.) and the hypothesis
becomes a real obligation. We picked unbundled here, with the
explicit understanding that this might need revisiting once a real
use case for the abstract `stroock_varopoulos` materializes.

## Operational rule

When proposing a structural definition in this project:

1. **List 2–3 concrete use cases** (typically: an existing instance
   in the codebase + a future use case from downstream
   `gaussian-hilbert` / `pphi2` / `lgt`).
2. **Try the bundled version first** at the whiteboard / draft
   level. Check that the statement of the use-case theorem types up
   cleanly without auxiliary lemmas.
3. **Try the unbundled version**. Check the same, and note what
   side hypotheses are needed.
4. **Consider the *carrier-set-as-data* pattern** (Gusakov–Nelson–
   Watt's matroid / graph case studies): when sub-objects, restriction,
   or deletion operations show up, an explicit carrier-set field is
   often cleaner than a type parameter — avoids cascading coercions.
5. **Compare**, paying attention to:
   - How clean the *use sites* are, not just the *definition*.
   - Whether junk values introduce vacuity / unsoundness traps
     (Bochner returns `0`, division-by-zero, `Real.log 0 = 0`, etc.).
   - Whether the unbundled version forces every call site to
     re-establish the missing property.
   - Whether sub-object operations are in the use-case list — if yes,
     carrier-set-as-data deserves a hard look.
6. **Have the proposed definition vetted** by `gemini-3.1-pro-preview`
   *before* writing the code. This is cheap and catches structural
   flaws that would otherwise show up multiple commits in.

This rule is meant to be applied to every non-trivial structural
choice: classes, structures, alternative carriers, what's a
hypothesis vs. a structure field, etc.

The three design-pattern axes to consider explicitly:

| Axis | Question | Worked example |
|---|---|---|
| Bundled vs. unbundled | Does the structure carry its laws/properties, or are they side hypotheses? | `MarkovSemigroup` vs `DirichletMarkovSemigroup` (this repo) |
| Strict typing vs. junk values | Do operations require domain conformance, or accept arbitrary input with default fallback? | Mathlib's `cfc` (unbundled) vs `cfcL` (bundled) |
| Type parameter vs. carrier set | Is the carrier a type-level argument, or an explicit field of the structure? | Mathlib's `Matroid`, `SimpleGraph` (carrier-set) |
